Introduction

[Back to Contents]

If you've spent your programming career in languages like Python, JavaScript, C#, or even C, stepping into Game Boy assembly language can feel like travelling back to the bare metal origins of computing. Everything you take for granted—variables, expressions, function calls, loops—must be constructed manually from the most primitive operations imaginable.

The Game Boy's processor is the Sharp SM83 (the CPU core inside the LR35902 chip), an 8-bit processor running at about 4.19 MHz. It is a cousin of the Zilog Z80 that powered the ZX Spectrum, Amstrad CPC and MSX machines, and of the Intel 8080 before it. Sharp kept most of the familiar instruction set, dropped the parts that cost chip area, and added a few new tricks of their own. The result is a CPU small enough to understand completely, in a machine that shipped over a hundred million units. Understanding Game Boy assembly gives you direct insight into how computers actually work at the lowest level.

This guide is a companion to the Z80 guide for the ZX Spectrum and follows it chapter by chapter, example by example. You do not need to have read that guide, or to have seen any assembly language before. It assumes you can already program. We won't explain what a loop is conceptually—we'll show you how to build one from nothing but jumps and flags. Each section maps a familiar high-level concept to its Game Boy equivalent, highlighting what changes and what stays the same.

Throughout this guide, all examples are written to be assembled using RGBDS (the rgbasm, rgblink and rgbfix tools), targeting the original monochrome Game Boy (DMG). This means every example can be built into a .gb ROM file and loaded directly into an emulator such as mGBA, or onto a real cartridge. Every example in this guide is also assembled and run in an emulator by an automated test suite, which checks what appears on the screen.

How to read assembly: the six ideas you need before you start.

  1. Instructions. An assembly program is a list of instructions, one per line. Each line is a short name, called a mnemonic, followed by the values it works on. LD A, 5 means "load": put the number 5 into A. The assembler turns each line into the bytes the CPU actually runs.
  2. Registers. The CPU has a handful of storage slots inside it, each with a one-letter name: A, B, C, D, E, H and L. Each holds one number from 0 to 255. Think of them as variables built into the processor. A is the busiest: most arithmetic happens in it. Some registers can team up in pairs (BC, DE and HL) to hold a bigger number, up to 65535.
  3. Memory. Besides the registers, the Game Boy has memory: a long row of numbered boxes, each holding one number from 0 to 255. A box's number is its address. Some memory is ROM (read-only: your program lives there and it cannot be changed) and some is RAM (you can store and change values in it).
  4. Numbers. Ordinary numbers are decimal. A $ in front means hexadecimal, so $FF is 255. Addresses are usually written in hexadecimal because it is tidier (for example $C000). A character in quotes, like 'A', stands for its character code (65).
  5. Comments and labels. Everything after a ; on a line is a comment for human readers. A name followed by a colon, like show:, is a label: it marks a place in the program so that you can refer to it by name.
  6. Subroutines. CALL show jumps to the label show, runs the instructions there, and comes back to the line after the CALL when it reaches RET (return). It is the assembly version of calling a function.
[[asm]] LD A, 5 ; put the number 5 into register A LD B, 3 ; put the number 3 into register B ADD A, B ; add B to A: A is now 8 CALL show ; run the routine labelled "show", then carry on here [[/asm]]

That is enough to start. Everything else is introduced in the chapter where it is first needed, and each chapter says what is different from a high-level language.

Debug Output Routines

[Back to Contents]

Throughout this guide, examples use a few small routines to display values on screen. These are your equivalent of console.log() or print() — a way to see what your code is actually doing. When you add two numbers and want to check the result, or need to verify that a conditional branch went the right way, these routines let you print the answer to the screen.

The Game Boy has no built-in text printing, so the routines come as three small files that you save next to your programs. You do not need to understand how they work to use them: this section shows you how to include them, and Appendix 1 at the end of the guide contains the full listing of each file and a step-by-step explanation, which is worth reading once you have finished the early chapters.

FileWhat it contains
hardware.incNames for the console's hardware settings, so that you can write rBGP instead of remembering the number $FF47
font.incThe pictures of the letters, digits and symbols
debug_output.asmThe routines themselves: debug_init, print_char, print_string and print_number

Copy each listing from Appendix 1 into a file with that name, in the same folder as the programs you write. (They are also in the gameboy_lib folder alongside this guide.)

Setting Up Your Editor

Before you write your first line of assembly, it helps to have an editor that understands Game Boy syntax. Visual Studio Code is a free, cross-platform editor that works well for this guide. Download and install it from https://code.visualstudio.com/ for Windows, macOS, or Linux.

Once VS Code is installed, add the RGBDS Z80 extension by Donald Hays. It provides syntax highlighting for RGBDS .asm files — coloured keywords, register names, directives, and comments — making your source code much easier to read and navigate.

To install it:

  1. Open VS Code and press Ctrl+Shift+X (Windows/Linux) or Cmd+Shift+X (macOS) to open the Extensions panel.
  2. Search for RGBDS Z80.
  3. Select the extension published by Donald Hays and click Install.

Alternatively, install it from the command line:

[[text]] code --install-extension donaldhays.rgbds-z80 [[/text]]

With the extension active, .asm files will have coloured keywords, register names, and comments.

Assembling with RGBDS

Every example in this guide is built with RGBDS, which is three small programs that you run one after another. rgbasm turns your source file into an object file. rgblink places the pieces at their final addresses and writes the ROM. rgbfix then fills in the cartridge header (the Nintendo logo, the title and the checksums) that a real Game Boy checks before it will run your program. Install RGBDS with your package manager (for example brew install rgbds on macOS) or download a ready-made build from https://rgbds.gbdev.io/.

The general form of the commands is:

[[text]] rgbasm -o program.o program.asm rgblink -o program.gb program.o rgbfix -v -p 0xFF program.gb [[/text]]

The -v flag tells rgbfix to write a valid header, and -p 0xFF pads the ROM out to a legal size. The -I . that you will see in the examples tells rgbasm to look for any files your program asks for in the current folder (the dot means "this folder"); the next section shows how a program asks for files. For example, to build a file called hello.asm:

[[text]] rgbasm -I . -o hello.o hello.asm rgblink -o hello.gb hello.o rgbfix -v -p 0xFF hello.gb [[/text]]

If rgbasm finds an error it will print the offending file and line number and a short message. Fix the error and re-run the commands. When all three succeed with no output, your .gb file is ready.

Running with mGBA

mGBA is an accurate, free Game Boy emulator with a built-in debugger. Once you have a .gb file, pass it directly to mGBA on the command line:

[[text]] mgba program.gb [[/text]]

So for the example above:

[[text]] mgba hello.gb [[/text]]

mGBA opens and your program starts at once. The output from your debug routines appears on the emulated screen. Close the mGBA window when you are done, edit your source file, re-assemble, and run again.

Your typical edit–assemble–run cycle from the terminal therefore looks like this (on Linux / Mac systems):

[[text]] rgbasm -I . -o hello.o hello.asm && rgblink -o hello.gb hello.o && rgbfix -v -p 0xFF hello.gb && mgba hello.gb [[/text]]

Chaining the commands with && means each step only runs if the one before it succeeded — a failed assembly stops the chain before the emulator opens. The gameboy_examples folder contains a Makefile that does exactly this for every example: make first.gb builds one, and make run-first builds and launches it.

Using the Routines

A program asks for another file with the INCLUDE directive. INCLUDE "hardware.inc" means "paste the contents of hardware.inc here". (A directive is an instruction to the assembler rather than to the CPU: it is not turned into code.) Every program in this guide follows the same pattern: INCLUDE "hardware.inc" on the first line, your own code in the middle, and INCLUDE "debug_output.asm" on the last line. The debug file includes font.inc by itself, so you never need to mention it.

The routines are used by loading a value into a register and then calling them, as in the Introduction. This table shows what each routine expects:

RoutineYou give itWhat it does
debug_initNothingSets up the screen. Call it once, at the start of your program
print_charA = a characterPrints one character
print_stringHL = the address where some text startsPrints text that ends with a zero byte
print_numberA = a number from 0 to 255Prints it in decimal

Printing one character is so common that it has a one-instruction shortcut: RST $10 does the same as CALL print_char (Chapter 12 explains how). The character code 13 means "start a new line". So the two most useful snippets are:

[[asm]] CALL debug_init ; Set up the screen (once, at the start) LD A, '*' ; Put the character '*' into A RST $10 ; Print it LD A, 13 ; 13 = new line RST $10 ; Move to the next line [[/asm]]

You will meet print_string and print_number in Chapter 2, where text and numbers are introduced, and Chapter 1 builds your first complete program. The screen shows 20 characters per line and 18 lines; text wraps at the end of a line.
