4. Control Flow: Conditionals

[Back to Contents]

In High-Level Languages

You write if/else blocks: if (x > 10) { doThis(); } else { doThat(); }. The language handles the branching logic invisibly.

In Game Boy Assembly

Conditionals work through two mechanisms: the flags register and conditional jumps. Every arithmetic or comparison instruction sets flags. You then use those flags to decide whether to jump.

The Flags Register

The F register contains several flag bits that reflect the result of the last operation:

Z (Zero): Set if the result was zero.

C (Carry): Set when a result does not fit in 8 bits. For addition, the carry flag is set if the result exceeds 255 — for example, 200 + 100 = 300, which is too large for a single byte, so the carry flag is set and A wraps around to 44 (300 - 256). For subtraction, the carry flag is set if the result would go below 0 — for example, 10 - 20 = -10, which is not a valid unsigned number, so the carry flag is set and A wraps around to 246 (256 - 10). Think of it as the CPU's way of saying "the answer didn't fit" — you can then check the carry flag to detect the overflow, or use ADC and SBC (explained below) to carry the extra bit into the next byte of a multi-byte calculation.

The carry flag is also used by two special arithmetic instructions: ADC (Add with Carry) and SBC (Subtract with Carry). These add or subtract as normal, but also include the carry flag in the calculation. This is how you do maths on numbers larger than 255 — the carry flag acts as the "1" you carry over when adding columns of digits by hand.

Suppose you want to add two numbers whose sum may not fit in a byte, and keep the result as a 16-bit value split across two registers (high byte in B, low byte in C). A single ADD can only handle 8 bits, so you add the low parts first, then use ADC to add the high parts with carry and pick up any overflow from the first addition:

[[asm]] ; Adding 200 + 100 = 300 ; These fit in single bytes, but their sum does not LD A, 200 ; A = 200 ADD A, 100 ; 200 + 100 = 300, but 300 > 255! ; A wraps to 44 (300 - 256), carry flag is SET LD C, A ; C = 44 (low byte) LD A, 0 ; High byte was 0 ADC A, 0 ; 0 + 0 + carry(1) = 1 LD B, A ; Result: B = 1, C = 44 → 256 + 44 = 300 [[/asm]]

The carry flag did the crucial work here. The low byte addition (200 + 100) overflowed past 255, so A wrapped around to 44 and the carry flag was set. When we then did ADC A, 0 on the high byte, it added 0 + 0 + 1 (the carry) = 1. The final result is split across B and C: B holds 1 (representing 256) and C holds 44, giving 256 + 44 = 300. This is exactly like carrying a digit in long addition.

Here is another example where the low bytes do not overflow, so the carry stays clear:

[[asm]] ; Adding 50 + 30 = 80 ; Both fit in a byte, and so does the result LD A, 50 ; A = 50 ADD A, 30 ; 50 + 30 = 80, no overflow, carry flag is CLEAR LD C, A ; C = 80 (low byte) LD A, 0 ; High byte was 0 ADC A, 0 ; 0 + 0 + carry(0) = 0 LD B, A ; Result: B = 0, C = 80 → just 80 [[/asm]]

This time the low bytes added up to 80, which fits in a single byte, so the carry flag stayed clear. ADC added 0 + 0 + 0 = 0, and the high byte remained zero. The same code handles both cases correctly — the carry flag automatically propagates the overflow when it happens and does nothing when it doesn't.

The same two-step idea adds two genuine 16-bit numbers, one held in HL and one in DE. Add the low bytes with ADD, then the high bytes with ADC so that a carry out of the low byte is included:

[[asm]] ; HL = HL + DE using 8-bit instructions (500 + 300 = 800) LD HL, 500 ; H = 1, L = 244 LD DE, 300 ; D = 1, E = 44 LD A, L ADD A, E ; 244 + 44 = 288: A = 32, carry SET LD L, A LD A, H ADC A, D ; 1 + 1 + carry(1) = 3 LD H, A ; HL = 3 * 256 + 32 = 800 [[/asm]]

The Game Boy also has a single instruction, ADD HL, DE, which adds the pair DE to the pair HL and does all of this at once. The long form is shown so you can see how the carry flag links the two halves. Be aware that there is no 16-bit ADC or SBC, so for 16-bit subtraction, or for sums of 24 or 32 bits, this byte-by-byte technique is the only way.

SBC works the same way but for subtraction — it subtracts the value and the carry flag. This handles the "borrow" when the low byte subtraction needs to take 1 from the high byte.

N (Subtract) and H (Half-carry): These two flags record whether the last operation was a subtraction, and whether a carry passed between the low and high four bits. They exist for an instruction (DAA) that helps with decimal arithmetic, which this guide does not need, so you will not use them.

Conditional Jumps

Jump instructions send execution to a label — a name you give to a specific point in your code, written as a word followed by a colon (e.g. my_label:). The assembler converts the label into a memory address for you. Labels also name subroutines, as you will see in the Functions section.

[[asm]] JP Z, label ; Jump if zero flag is set JP NZ, label ; Jump if zero flag is NOT set JP C, label ; Jump if carry flag is set JP NC, label ; Jump if carry flag is NOT set JP label ; Always jump [[/asm]]

There is also JR (Jump Relative), which works the same way but encodes the destination as an offset from the current position rather than an absolute address. JR is one byte smaller than JP, but it can only jump within -128 to +127 bytes of the current instruction. On the Game Boy, JP and JR both support the same four conditions: Z, NZ, C, and NC. Use JR for short, nearby branches and JP when the target is far away.

No sign flag: Some processors have a flag that says "the last result was negative". The Game Boy does not, so there is no "jump if negative". To find out whether an 8-bit value is negative (its leftmost bit is 1) you test that bit directly. BIT 7, A tests bit number 7 of A (counting from 0 on the right, so bit 7 is the leftmost) and sets the Zero flag if that bit is 0; so BIT 7, A followed by JR NZ, is_negative jumps when the number is negative.

Comparison

[[asm]] CP B ; Compare A with B (sets flags, doesn't change A) CP 100 ; Compare A with 100 [[/asm]]

The CP instruction subtracts without storing the result — it only sets the flags. A is unchanged afterwards. You then use a conditional jump to act on the result:

[[asm]] CP 10 ; Subtract 10 from A (but don't store the result) JR Z, is_ten ; Jump if A was equal to 10 (Zero flag set) JR C, less_than ; Jump if A was less than 10 (Carry flag set) ; If we reach here, A was greater than 10 [[/asm]]

Think of it as asking a question: CP asks "how does A compare?", and the conditional jump acts on the answer. The common patterns are:

  • CP n then JR Z — jump if A equals n
  • CP n then JR NZ — jump if A does not equal n
  • CP n then JR C — jump if A is less than n
  • CP n then JR NC — jump if A is greater than or equal to n

Key Difference: There's no implicit 'else' structure. You must explicitly jump over blocks you don't want to execute. Every branch is a goto by another name. The structure exists only in how you lay out your labels and jumps.

5. Control Flow: Loops

[Back to Contents]

In High-Level Languages

Loops have dedicated syntax: for, while, do-while, foreach. The language manages the iteration variable, the condition check, and the repetition.

In Game Boy Assembly

Loops are built from labels, conditional jumps, and decrement instructions.

Counted Loops

A counted loop puts the number of repeats in a register, runs the body, subtracts one, and jumps back until the register reaches zero. DEC B subtracts one from B and sets the Zero flag when the result is 0, and JR NZ ("jump if the Zero flag is not set") does the jumping:

[[asm]] LD B, 10 ; Loop 10 times loop_start: ; ... loop body ... DEC B ; Decrement B (sets the Zero flag when it reaches 0) JR NZ, loop_start ; Jump back if B != 0 [[/asm]]

This is the assembly equivalent of for (int i = 10; i > 0; i--). Note that it counts down, not up, and by convention uses the B register (any register will do, since you are using plain DEC). It also decrements before testing, so if B is 0 when the loop starts, B wraps to 255 and the body runs 256 times. Check for zero first if the count can be zero. (If you know the Z80: it has a single instruction, DJNZ, that does the DEC B and JR NZ together. The Game Boy has no DJNZ, so you write both.)

While Loop

A while loop tests a condition at the top and repeats until that condition is false. Here is the general pattern — it loads the variable from memory on every iteration, checks it, does the work, stores it back, and loops:

[[asm]] ; while (a != 0) { a--; } LD A, 5 ; Starting value — the loop will run 5 times LD [var_a], A while_start: LD A, [var_a] ; Load the current value from memory into A CP 0 ; Is it 0? JP Z, while_end ; If yes, exit the loop DEC A ; Subtract 1 LD [var_a], A ; Store the new value back to memory JP while_start ; Jump back to the top and check again while_end: SECTION "Loop variable", WRAM0 var_a: DS 1 [[/asm]]

Notice that A is loaded from memory every time around the loop. Why? Because the CPU cannot work on a memory location named by a label directly — CP [var_a] and DEC [var_a] do not exist. Only the pointer form [HL] can be used with instructions like DEC [HL] or CP [HL]. So when the variable lives at a label, the pattern is: load from memory, work on it in a register, store it back. Note too that the starting value is stored at run time, because RAM cannot be given a starting value in the source the way ROM data can.

In this simple case, though, that reload is wasteful. After DEC A, the register already holds the updated value — there is no need to store it and immediately load it again. A more efficient version keeps everything in A and only touches memory at the start and end:

[[asm]] ; Same result, but faster — no unnecessary memory access inside the loop LD A, [var_a] ; Load once before the loop while_start: CP 0 ; Is A 0? JP Z, while_end ; If yes, done DEC A ; A still holds the value — no need to reload JP while_start ; Loop back (A carries the value with it) while_end: LD [var_a], A ; Store the final result (0) back to memory [[/asm]]

The first version is the safe, general pattern — you would need it if the loop body used A for other things (like printing or calling a subroutine) and its value got overwritten. The second version works when nothing else in the loop touches A, so the value survives from one iteration to the next.

Iterating Over an Array

Here is how to sum all bytes in an array and display the result. The simplest approach is to hardcode the length:

[[asm]] LD HL, my_array ; Point HL at start of array LD B, 5 ; Array length — hardcoded XOR A ; Clear A (running total) sum_loop: ADD A, [HL] ; Add current byte to total INC HL ; Move to next byte DEC B ; One fewer to go JR NZ, sum_loop ; Repeat B times CALL print_number ; Display the sum on screen LD A, 13 RST $10 ; Newline my_array: DB 10, 20, 30, 40, 50 [[/asm]]

This works, but the length is baked into the code. If you add or remove elements from the array, you must remember to update the LD B, 5 line as well — a common source of bugs.

A better approach is to make the array carry its own length as the first byte. The data follows immediately after:

[[asm]] my_array: DB 5, 10, 20, 30, 40, 50 ; ^ ^--- the actual data starts here ; | ; length byte (5 elements follow) [[/asm]]

Now the loop reads the length at runtime instead of having it hardcoded:

[[asm]] LD HL, my_array ; HL points to the length byte LD B, [HL] ; B = first byte = 5 (the length) INC HL ; Move HL past the length byte to the actual data XOR A ; Clear A (running total) sum_loop: ADD A, [HL] ; Add current byte to total INC HL ; Move to next byte DEC B ; One fewer to go JR NZ, sum_loop ; Repeat B times CALL print_number ; Display the sum on screen LD A, 13 RST $10 ; Newline [[/asm]]

With this approach, you can change the array data freely — just keep the length byte accurate. The CPU has no built-in way to know how long an array is, so you must always track the length yourself, either by hardcoding it, storing it alongside the data like this, or using a terminator value (like the null terminator we use for strings).

Adding a Value to an Array

In a high-level language, adding to an array is simple — my_array.push(60) or my_array.append(60). The language handles resizing the array if needed. In assembly, there is no resizing. Memory is fixed. If you want to add elements at runtime, the array must live in RAM, and you must reserve extra space upfront. Because RAM has no starting values, we also fill in the first few elements by hand:

[[asm]] SECTION "Array", WRAM0 my_array: DS 9 ; Length byte + room for 8 values (3 used, 5 spare) SECTION "Array setup", ROM0 LD HL, my_array LD A, 3 LD [HL+], A ; Length byte: 3 values follow LD A, 10 LD [HL+], A LD A, 20 LD [HL+], A LD A, 30 LD [HL+], A [[/asm]]

(The two lines that start with SECTION are declarations: the first reserves the array's memory, and the second says that the instructions after it are ordinary program code that you would put in your main code.) The array currently holds 3 elements but has room for up to 8. (Another common technique is to keep the starting values in ROM and copy them into RAM with a loop when the program starts.) To add the value 60 to the end, we need to: read the current length, calculate where the new element goes, write it there, and update the length byte:

[[asm]] ; Add 60 to the end of my_array LD HL, my_array ; HL points to the length byte LD A, [HL] ; A = current length (3) INC A ; A = new length (4) LD [HL], A ; Update the length byte in memory LD D, 0 LD E, A ; DE = new length (4) ADD HL, DE ; Add DE to HL: HL = my_array + 4 = address of the new last element LD [HL], 60 ; Write 60 there [[/asm]]

After this, the array in memory is: 4, 10, 20, 30, 60 — the length byte has been updated to 4 and the new value sits at the end.

There is no bounds checking. If you add more elements than you reserved space for, you will silently overwrite whatever comes next in memory — other variables, other code, anything. There is no error, no warning. It is entirely your responsibility to check the length before adding and make sure you do not exceed the reserved space.

Key Difference: Infinite loops are trivially easy—just JP back to a label with no exit condition. There's no for-each; you manually track the pointer and count. Off-by-one errors are common and unforgiving.

Try It Yourself

Copy the program below into VS Code, save it as loops.asm, then assemble and run it. It cycles the whole screen through all four shades of the Game Boy's display, holding each one for about half a second so you can see it change. It uses both loop patterns from this section at the same time: a countdown loop for the delay, and a while-style outer loop to step through the shades.

The shade of the screen is set with the palette register rBGP that you met in Chapter 3. If we write the same shade number into all four of its 2-bit slots, every dot on the screen becomes that shade. The four values that do this are $00 (all shade 0, white), $55 (%01010101, all shade 1), $AA (%10101010, all shade 2) and $FF (all shade 3, black). Each is $55 more than the one before, which gives the outer loop a neat way to stop: after $FF, adding $55 again overflows a byte, and the carry flag tells us so.

The delay is a loop of its own, counting the pair BC down from 65536. There is one wrinkle: DEC BC (decrement a 16-bit pair) does not set the Zero flag, so we cannot simply follow it with JR NZ. Instead we copy B into A and OR it with C: the result is zero only if both B and C are zero, and OR does set the flag. Each lap takes seven machine cycles of the CPU's clock, which runs at about a million machine cycles a second, so 65536 laps take about 0.44 seconds, long enough to see each shade clearly.
