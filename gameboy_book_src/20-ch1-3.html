1. Introduction & Setup

[Back to Contents]

In High-Level Languages

You install a runtime or compiler, create a source file, and run a command. Python gives you an interpreter, Node gives you a runtime, C gives you a compiler that produces an executable. The toolchain handles the translation from your text to something the machine understands.

In Game Boy Assembly with RGBDS

You need two things: RGBDS (the assembler toolchain) to translate your mnemonics into machine code, and an emulator to run the result. That's it.

RGBDS is a cross-assembler for the Game Boy. It is three programs: rgbasm assembles, rgblink links and places the code in a ROM, and rgbfix writes the cartridge header. The result is a .gb file, the same format that is burned into a real cartridge, so everything you build here will also run on real hardware.

Emulator: For Game Boy development, mGBA is excellent and freely available for all major operating systems, and it has a built-in debugger. SameBoy and BGB are good alternatives. They all load .gb files directly.

Your Workflow

The development cycle is simple. Write your assembly code in a .asm file. Assemble it with RGBDS. Load the resulting .gb file in mGBA. Here is your first complete program, which prints an asterisk. Every Game Boy program in this guide has the same five parts, and this one shows them all:

  1. INCLUDE "hardware.inc": the names of the hardware settings (see Debug Output Routines).
  2. A fixed block of lines that you copy unchanged: it marks the place where the console starts running your cartridge.
  3. Your own code, beginning at a label called Start.
  4. A few lines at the end, labelled Done, that stop the CPU (a Game Boy program never finishes the way a desktop program does).
  5. INCLUDE "debug_output.asm": the printing routines.
[[file first.asm]]

Walking through it, part by part:

SECTION "Header", ROM0[$100] tells the assembler where to put the lines that follow. A section is a named block of the program; ROM0 means it goes in the cartridge ROM, and [$100] says it must start at address $100 (256). That address is where the console starts running your cartridge, once its tiny built-in start-up program (the boot ROM, which scrolls the logo) has finished. There is room for only four bytes there, so we put two instructions: NOP ("no operation": do nothing) and JP Start (jump: carry on from the label Start, like a goto). DS $150 - @, 0 fills the rest of the gap, up to address $150, with zeros: DS means "define space", and @ means "the address we have reached so far". That gap is where the cartridge header goes; rgbfix writes it for us later.

SECTION "Main", ROM0[$150] starts a second section at $150, and this is where your own code goes. The linker (rgblink) checks that no two sections overlap. The first line there is CALL debug_init to set up the screen. LD A, 42 loads the number 42 (the character code of an asterisk) into A, and RST $10 prints it, exactly as in the previous section.

The last three lines are the ending. HALT stops the CPU until a hardware signal called an interrupt arrives (Chapter 9 covers interrupts). We have not asked for any, so the CPU sleeps until the console is switched off. NOP after it is a safety habit that Chapter 9 explains, and JR Done (a short jump back to the label Done) means that even if the CPU wakes up it just goes back to sleep, rather than running on into whatever bytes follow.

Assemble:

[[text]] rgbasm -I . -o first.o first.asm rgblink -o first.gb first.o rgbfix -v -p 0xFF first.gb [[/text]]

Then open first.gb in mGBA.

[[text]] mgba first.gb [[/text]]

The ROM starts running at once. You should see an asterisk printed in the top left corner of the screen.

Key Difference: There's no operating system, and no BASIC to return to. The Game Boy's boot ROM runs once at power-on and then disappears, so when your program reaches the end there is nowhere to RET to. That is why every program ends by parking the CPU in the Done loop.

2. Variables & Data Types

[Back to Contents]

In High-Level Languages

You declare variables with names and types: let count = 0, int age = 25, name = "Alice". The language manages where these values are stored, handles type conversions, and lets you refer to them by name throughout your code.

In Game Boy Assembly

There are no variables in the high-level sense. You have two places to store data: registers and memory. That's it.

Registers

The Game Boy's CPU has a small set of registers—tiny, fast storage locations inside the processor itself:

A (Accumulator): The primary register for arithmetic and logic. Most operations use A as one operand and store results back in A.

B, C, D, E, H, L: General-purpose 8-bit registers. Can also be paired as BC, DE, and HL for 16-bit values.

HL: Often used as a pointer to memory. Many instructions work with the memory location that HL points to, written as [HL].

SP: Stack pointer—points to the current top of the stack.

PC: Program counter—the address of the next instruction. You don't manipulate this directly; jumps and calls change it.

F: Flags register—holds the results of comparisons and arithmetic, as a few on/off switches called flags. The important ones are zero (Z, "the last result was 0") and carry (C, "the last result didn't fit in a byte"). Chapter 4 shows how to use them to make decisions.

If you know the Z80, what's different? (Everyone else can skip this box.) The Game Boy CPU has no IX/IY registers, no shadow registers (so no EX or EXX), no IN/OUT instructions (hardware is reached through memory addresses instead), no DJNZ, no LDIR/LDDR block moves, and no 16-bit ADC/SBC. It adds LDH (a short form for the $FF00 hardware area), LD A,[HL+] and LD A,[HL-] (load and step the pointer), SWAP (swap the two halves of a byte), and STOP. This guide points out each difference where it first matters.

Data Types

There are only two 'types': bytes (8-bit, 0–255) and words (16-bit, 0–65535). A byte can also be read as a signed number, –128 to 127, where a 1 in the leftmost bit means negative; the CPU stores both kinds the same way and it is up to you which you mean. Everything else—strings, arrays, structures—you build yourself from these primitives.

[[asm]] ; Defining data in memory my_byte: DB 42 ; Define a single byte with value 42 my_word: DW 1000 ; Define a 16-bit word (low byte first) my_string: DB "Hello", 0 ; String is just bytes, null-terminated my_array: DB 1, 2, 3, 4, 5 ; Array is just consecutive bytes [[/asm]]

DB means 'define byte', DW means 'define word'. The labels (my_byte, my_word, etc.) are just names for memory addresses—the assembler replaces them with actual numbers. A word takes two bytes, and the Game Boy stores the low byte first: 1000 is $03E8, so DW 1000 stores $E8 and then $03. This order is called little-endian, and you will see it again whenever a 16-bit value is kept in memory.

A string in assembly is just a sequence of bytes in memory, one per character, with a zero byte at the end to mark where the string finishes. This zero byte is called the null terminator — it is how a routine that prints the string knows when to stop. In my_string above, the text in quotes is a shorthand — the assembler converts each character to its character code and stores them as consecutive bytes (72, 101, 108, 108, 111). The comma separates items in the DB list, so you can mix quoted strings with individual byte values. The 0 after the comma is a single byte with the value zero — the null terminator. It does not represent the character '0' (which would be code 48); it is literally the value 0.

There is one important rule about where data lives. Everything defined with DB or DW in your code lives in the cartridge ROM, and ROM cannot be written to. That is perfect for constants, strings and lookup tables. For anything your program needs to change (a score, a counter, a cursor position) you must reserve space in the console's RAM, which starts at address $C000, using a WRAM0 section and the DS directive:

[[asm]] SECTION "Variables", WRAM0 my_counter: DS 1 ; One byte of RAM that we are allowed to change [[/asm]]

Loading and Storing

[[asm]] ; Loading values LD A, 10 ; Load immediate value 10 into A LD B, A ; Copy A into B LD A, [my_byte] ; Load value FROM memory address my_byte into A LD HL, my_array ; Load the ADDRESS of my_array into HL LD A, [HL] ; Load the byte that HL points to into A ; Storing values (the target must be RAM, not ROM) LD [my_counter], A ; Store A's value TO memory address my_counter LD HL, my_counter LD [HL], 99 ; Store 99 at the address HL points to LD A, [HL+] ; Load the byte HL points to, THEN add 1 to HL [[/asm]]

Square brackets mean "the contents at this address". This is the single most important syntax rule in Game Boy assembly. Without brackets, you get the address itself; with brackets, you get the value stored at that address. Compare these two instructions:

[[asm]] LD A, [my_byte] ; A = the value stored at my_byte's address (e.g. 42) LD HL, my_byte ; HL = the address of my_byte itself (e.g. $0300) [[/asm]]

In the first line, the brackets tell the CPU: "go to the address labelled my_byte, read the byte stored there, and put it in A." In the second line, there are no brackets, so the CPU simply loads the address number into HL — it never looks at what is stored there. This is the difference between reading a value from a postbox and writing down the postbox's location. Both are useful, but mixing them up is one of the most common beginner mistakes in Game Boy programming.

Notice the last line of the first listing: LD A, [HL+]. It reads the byte and moves the pointer on in a single instruction, which is exactly what you need when walking through an array or a string. Its mirror image LD [HL+], A stores and advances, and [HL-] steps backwards. (The Z80 has no such instruction.)

To verify that your loads and stores are working, use the debug routines:

[[asm]] LD A, [my_byte] ; Load the value CALL print_number ; Display it on screen - should show 42 LD A, 13 RST $10 ; Newline [[/asm]]

Key Difference: There's no type checking, no automatic conversion, no protection. If you write a 16-bit value to an 8-bit location, you'll overwrite whatever's next in memory. You must track what's stored where. And if you try to store to an address in ROM, nothing happens at all—the write is silently ignored.

Try It Yourself

Copy the program below into VS Code, save it as variables.asm in the same folder as debug_output.asm, then assemble and run it. It loads and displays each of the data types defined above so you can see exactly what gets stored where. It uses the two remaining debug routines from the Debug Output Routines section:

  • print_number prints the number in A as ordinary decimal digits: load 42 into A, CALL print_number, and "42" appears.
  • print_string prints a string. It needs to be told where the string is, so you put the string's address in HL (the label of the string, loaded without brackets) and CALL print_string. It prints characters until it reaches the null terminator.

For the array, we point HL at the first element and step through it with INC HL (INC means "increment": add one, so INC HL moves the pointer on to the next byte). There is one trap. The routines we call are allowed to use HL internally and leave it pointing somewhere else, so a pointer you stored in HL may be gone by the time the call returns. The fix is to preserve HL across each call using the stack. The stack is a scratch area of memory where you can set a value aside and get it back later (Chapter 6 covers it fully). PUSH HL sets HL's current value aside before the call, and POP HL gets it back afterwards. Then INC HL advances the pointer to the next element as normal. This push-call-pop pattern is the standard technique for protecting a register across a subroutine call that might clobber it.

[[file variables.asm]]

Expected output on screen:

[[text]] my_byte: 42 my_string: Hello my_array: 1 2 3 4 5 [[/text]]

3. Operators & Expressions

[Back to Contents]

In High-Level Languages

Expressions combine values with operators: result = (a + b) * c - d / 2. The compiler figures out the order of operations, allocates temporary storage, and generates all necessary instructions automatically.

In Game Boy Assembly

There are no expressions. Each operation is a separate instruction, and results almost always go into the accumulator (A). To compute (a + b) * c, you must break it down step by step.

Arithmetic Instructions

[[asm]] ; Addition ADD A, B ; A = A + B ADD A, 5 ; A = A + 5 ; Subtraction SUB B ; A = A - B SUB 10 ; A = A - 10 ; Increment / Decrement INC A ; A = A + 1 DEC B ; B = B - 1 INC HL ; HL = HL + 1 (16-bit increment) [[/asm]]

Logic Instructions

These instructions work on individual bits. Each bit in A is compared with the corresponding bit in the other register, one bit at a time. The examples below use the % prefix to write numbers in binary (e.g. %00000001 is the value 1, with each digit representing one bit). This makes it easy to see exactly which bits are being affected:

Bitwise vs logical — an important distinction. In a high-level language, AND and OR are usually logical operators that treat entire values as either true or false: 3 AND 5 evaluates to true because both values are non-zero. On the Game Boy, AND and OR are bitwise — they operate on each of the 8 bits independently. This means the result depends on the bit patterns, not the overall values. For example, if A = 3 and B = 5:

[[asm]] ; A = 3 → 00000011 ; B = 5 → 00000101 ; AND B result → 00000001 (only bit 0 is 1 in both — result is 1, not 3 or 5) ; OR B result → 00000111 (bits 0, 1, and 2 are set in at least one — result is 7) [[/asm]]

If you come from Python or C and expect AND to mean "are both of these things true?", you will get unexpected results. The CPU does not care whether a value is "truthy" — it lines up the bits and compares them one by one. There is no logical AND or OR. You get bitwise operations only, and they are powerful once you think in terms of individual bits rather than whole numbers.

[[asm]] AND B ; A = A AND B OR C ; A = A OR C XOR A ; A = A XOR A (quick way to set A to 0) CPL ; A = NOT A (flip every bit) [[/asm]]

AND — a bit in the result is 1 only if that bit is 1 in both inputs. If either bit is 0, the result is 0. This is useful for masking out bits you don't care about. For example, AND with 00001111 keeps only the lower four bits and clears the upper four.

[[asm]] ; Keep only the lower four bits of a value LD A, %10110110 ; A = 10110110 AND %00001111 ; Mask: keep the four right-hand bits, clear the four left-hand bits ; A is now %00000110 (6) [[/asm]]

OR — a bit in the result is 1 if that bit is 1 in either input (or both). The only way a bit ends up 0 is if it is 0 in both inputs. This is useful for setting specific bits without disturbing the others.

[[asm]] ; Suppose a byte of memory holds eight on/off settings, one per bit, ; and HL points at it. To switch setting number 5 on without changing ; the other seven: LD A, [HL] ; Read the current settings byte OR %00100000 ; Force bit 5 to 1 — setting 5 is now on LD [HL], A ; Write it back — the other seven settings are unchanged [[/asm]]

XOR — a bit in the result is 1 if the two inputs are different, and 0 if they are the same. This is why XOR A with itself always gives 0 — every bit matches, so every result bit is 0. It is the fastest way to clear A on the Game Boy (one byte long and the quickest instruction there is, versus two bytes for LD A, 0). XOR is also useful for toggling bits on and off:

[[asm]] ; Toggle setting number 6 — if it was on, turn it off; ; if it was off, turn it on: LD A, [HL] ; Read the current settings byte XOR %01000000 ; Flip bit 6 — toggles that setting LD [HL], A ; Write it back [[/asm]]

CPL — flips every bit in A. Every 1 becomes 0 and every 0 becomes 1. For example, if A is 00110101, after CPL it becomes 11001010. One common use is inverting a picture so it shows up against any background:

[[asm]] ; A byte can hold one row of eight pixels, one bit per pixel. ; To get the negative image of the row: LD A, [HL] ; Read a byte of picture data CPL ; Invert it — every pixel flips ; Now A holds the negative image of that row [[/asm]]

The Game Boy also has an instruction that the Z80 lacks: SWAP, which exchanges the top four bits of a register with the bottom four. SWAP A turns %11110000 into %00001111, and %00010011 into %00110001. It is handy for splitting a byte into two hexadecimal digits.

Building an Expression

Let's compute result = (10 + 5) * 2 and verify the answer:

[[asm]] LD A, 10 ; A = 10 LD B, 5 ; B = 5 ADD A, B ; A = 10 + 5 = 15 ADD A, A ; A = 15 * 2 = 30 (adding to itself) ; Verify the result using debug output CALL print_number ; Should display 30 [[/asm]]

Notice there's no multiply instruction. For multiplying by 2, you add the value to itself, as above. For general multiplication, you must implement it with loops (Chapter 5) or lookup tables.

Key Difference: The Game Boy CPU has no MUL or DIV instructions. Multiplication and division must be implemented in software, typically through repeated addition/subtraction. This is why early games often used sizes and speeds that were easy to build from doubling.

Try It Yourself

Copy the program below into VS Code, save it as bitwise.asm alongside debug_output.asm, then assemble and run it. Rather than just printing numbers, this example uses AND and OR to directly manipulate a hardware register — producing a visible effect on screen.

A hardware register is a byte of memory that is wired straight to part of the console. Writing to it changes what the hardware does, and you read and write it with the same LD instruction as any variable. The one we use here is called rBGP (the name comes from hardware.inc), the background palette. Everything on the Game Boy screen is made of dots that each have a colour number from 0 to 3, and the palette says which of the four shades the display actually shows for each colour number: 0 is the lightest and 3 the darkest. The palette packs four 2-bit numbers into one byte:

[[asm]] ; Bit 7 Bit 6 Bit 5 Bit 4 Bit 3 Bit 2 Bit 1 Bit 0 ; Colour 3 shade Colour 2 shade Colour 1 shade Colour 0 shade ; ; Colour 3 — the dots that make up the letters when text is printed ; Colour 0 — the empty background ; A shade is 0 (lightest), 1, 2 or 3 (darkest) [[/asm]]

The debug routines set the palette to %11100100, which gives colour 0 the shade 0 (white) and colour 3 the shade 3 (black): black letters on a white screen. This is exactly the kind of problem AND and OR are designed for. OR sets specific bits to 1 without touching anything else — here it will force the two lowest bits to 1, so the background becomes shade 3, black. AND clears specific bits to 0 without touching anything else — here it will clear the two highest bits, so the letters become shade 0, white. The four middle bits, the shades of colours 1 and 2, are never disturbed because they are not part of either mask.

[[file bitwise.asm]]

You should see INVERT! appear in the top left of the screen in white letters on a black background. First the text was printed in black on white; OR then turned the background black (so for a moment the black letters vanished into it), and AND finally turned the letters white. Both effects come from changing just two bits in one byte.
