3. Drawing Pixels

[Back to Contents]

In High-Level Languages

Plotting a pixel is the most basic graphics operation: canvas[y][x] = colour, usually wrapped in a function that also checks that the coordinates are on the canvas and silently ignores them if not. Every line, circle and flood fill is built on it.

[[text]] function setPixel(x, y, colour): if x < 0 or x >= width or y < 0 or y >= height: return framebuffer[y * width + x] = colour [[/text]]

The function is cheap on a PC because memory is byte-addressed and a pixel is a whole byte or more. On the Game Boy a pixel is two bits, in two different bytes, and the memory it lives in cannot even be written most of the time.

In Game Boy Assembly

The Game Boy is a tile machine, so most pictures are made by placing tiles, not by plotting pixels (Chapters 1, 5 and 6). But sometimes you do want to draw: a graph, a drawing tool, a procedurally generated shape, a line-drawn map. The trick is to turn tiles into a canvas.

VRAM holds 256 tiles at $8000-$8FFF. If the map arranges tiles 0–255 in a 16×16 block, in order, those 256 tiles together form a 128×128 pixel picture, and drawing a pixel means changing the right two bits of the right tile. That is the canvas.

One problem remains: VRAM can only be written in VBlank, and plotting a pixel is slow. So the canvas lives in work RAM, in exactly the layout VRAM wants — 4,096 bytes at $D000 — and is copied into VRAM when a picture is ready (LCD off), or tile by tile as things change.

Where a pixel lives

Pixel (x, y) is in tile column x / 8, tile row y / 8. Each tile row of the canvas is 16 tiles × 16 bytes = 256 bytes, which is exactly one page. So:

[[text]] address high byte = $D0 + y / 8 address low byte = (x / 8) * 16 + (y mod 8) * 2 bit mask = $80 >> (x mod 8) [[/text]]

The low byte of the address is the tile within its row ((x / 8) × 16) plus two bytes for each line down inside the tile. The pixel's colour is spread over the byte at that address (bit 0 of the colour) and the next one (bit 1). The mask picks the pixel's column: leftmost pixel is bit 7. There is no loop and no multiplication: shifts and masks only.

The canvas is 128 pixels square, so a coordinate of 128 or more is off it. plot checks for this first — OR the two coordinates together and test bit 7 — and quietly does nothing, so every other routine in this and the next two chapters can be drawn partly or wholly off the edge without damaging memory. A “negative” coordinate is 128–255 as an unsigned byte and is ignored for the same reason.

Setting, clearing and inverting

To give the pixel colour 0–3, the program sets or clears the mask bit in each of the two bytes: OR sets it, AND with the inverted mask clears it.

[[part canvas.asm | plot: | ; --- Invert pixel]]

Inverting a pixel flips both planes with XOR, which swaps colour 0 with 3 and colour 1 with 2. It is the way to draw something that can be removed again by drawing it a second time.

[[part canvas.asm | toggle_pixel: | ; --- Horizontal line]]

Clearing the canvas and showing it

Clearing is easy because colours are two bit-planes: colour 3 is every byte $FF, colour 0 every byte $00, and colours 1 and 2 alternate $FF and $00.

[[part canvas.asm | ; --- Fill the whole canvas | ; --- Work out where a pixel]]

Showing the canvas is two jobs: arrange the map so tile 0 is at one corner, tile 1 next to it, and so on (canvas_map); and copy the 4,096 bytes into tile memory (canvas_to_vram). The canvas map fills 16 entries per row with consecutive numbers, then skips to the next map row, which is 32 entries on.

Copying all 4,096 bytes takes far longer than a VBlank, which is why this program uses the LCD-off method. A program that animates a drawing would instead copy only the 16-byte tiles that changed each frame, in VBlank (Chapters 9 and 10).

Key fact: a Game Boy pixel is two bits in two bytes. Build pictures in RAM, in the same layout as VRAM, and copy them across in bulk — then a pixel is a shift, a mask and two writes.

4. Drawing Lines

[Back to Contents]

In High-Level Languages

A line is drawLine(x0, y0, x1, y1). The library decides which pixels to light, usually with Bresenham's algorithm, and calls setPixel for each. Horizontal and vertical lines get special cases, because they can be filled without any maths. Thicker lines are built from several thin ones, or from filled shapes along the path.

[[text]] drawLine(0, 0, 10, 4): for x in 0..10: setPixel(x, round(x * 4 / 10), colour) [[/text]]

That one-liner uses floating point. The point of Bresenham is that integers are enough, and that matters a great deal when the CPU has no multiply or divide instruction at all.

In Game Boy Assembly

There are two entirely different ways to draw a line on a tile machine, and a good program uses both.

Lines made of tiles

If a line is horizontal or vertical and its thickness can be 8 pixels or a whole tile, you do not need pixels at all. A wall, a platform, a dialog border or a graph axis is just a row of identical tile numbers. Because the map is linear, a horizontal line is consecutive bytes and a vertical line is bytes 32 apart.

The program keeps a copy of the map in work RAM (a shadow map), draws into that, and copies the finished map to VRAM. Lines in it are just loops over shadow_set:

[[part tilemap.asm | ; --- A line made of tiles | shadow_to_vram:]]

A box is four of these. No bit-masks, no planes: 12 map writes for a 12-tile line, against 96 pixel plots for the same width on the canvas.

Lines made of pixels

For anything at an angle, or one pixel thick, you go back to the canvas of Chapter 3. Horizontal and vertical lines are loops of plot:

[[part canvas.asm | ; --- Horizontal line | ; --- Bresenham line]]

Bresenham's algorithm

For a diagonal, the program steps along the longer axis one pixel at a time and decides, at each step, whether to move the shorter axis too. It keeps a running total: each step adds the short distance, and whenever the total reaches the long distance, the short axis steps and the total drops by the long distance. That is the whole algorithm. Starting the total at half the long distance makes the line round evenly at both ends.

Say the line goes from (0, 0) to (10, 4). The long axis is x (10 steps) and the short distance is 4. The total starts at 5, half of 10. Each row below is one plotted pixel, then the addition of 4 to the total:

[[text]] plot total after adding 4 y steps? (0, 0) 9 no (9 is less than 10) (1, 0) 13 - 10 = 3 yes (2, 1) 7 no (3, 1) 11 - 10 = 1 yes (4, 2) 5 no (5, 2) 9 no (6, 2) 13 - 10 = 3 yes (7, 3) 7 no (8, 3) 11 - 10 = 1 yes (9, 4) 5 no (10, 4) (the last pixel, so we stop) [[/text]]

Four y steps over ten x steps: the line rises 4 as it runs 10, with the rises spread as evenly as whole pixels allow.

Everything fits in 8 bits for a 128-pixel canvas: the total never exceeds twice the longer distance, which is under 256. That avoids the signed 16-bit arithmetic the textbook version needs.

[[part canvas.asm | draw_line: | ; --- Rectangles]]

The routine first works out the distance and the direction (±1) on each axis, picks the longer one, then loops, plotting and stepping. The step helpers step_x and step_y add the direction to the current coordinate. The same loop handles all eight octants, because the “which axis is long” question is answered once, up front, and stored in wSteep.

Key fact: use tiles for straight lines of tile thickness, and the pixel canvas for everything else. Bresenham needs only an accumulator and a comparison, and fits in 8-bit arithmetic on a small canvas.

5. Drawing Shapes

[Back to Contents]

In High-Level Languages

Shape functions — drawRect, fillRect, drawCircle, floodFill — are built from lines and pixels. A filled rectangle is a loop of horizontal lines; a circle uses its eight-way symmetry; and a flood fill is a search that spreads outward from a seed pixel until it meets a different colour, often written recursively or with a stack of pixels still to visit.

[[text]] floodFill(x, y, new): old = pixel(x, y) stack = [(x, y)] while stack: (px, py) = pop; if pixel(px, py) == old: set it to new; push the four neighbours [[/text]]

On a PC each of these touches many individual pixels. The question for the Game Boy is how many of them can be avoided.

In Game Boy Assembly

The same two routes apply: shapes made of tiles and shapes made of pixels.

Rectangles

A hollow rectangle is four lines. On the tile map, that is two shadow_hline and two shadow_vline calls, and a filled rectangle is one shadow_hline per row — or, if the map is being cleared, a single fill_bytes. On the canvas the pixel versions are:

[[part canvas.asm | ; --- Rectangles | ; --- Circles (midpoint]]

Circles

Circles use the midpoint algorithm, which exploits the circle's eight-fold symmetry: it only works out one eighth of the circle (from the top, going right and down) and mirrors each point to the other seven positions. Starting at (radius, 0), each step moves y up by one, and x down by one whenever an error term says the circle has crossed into the inner pixel.

[[part canvas.asm | ; --- Circles (midpoint | circle_setup:]]

The error term can be negative and exceeds 8 bits, so it is a 16-bit signed value kept in two bytes. Setting it up is 1 − radius; SBC A after the subtraction turns the borrow into the high byte ($FF for negative, $00 for positive):

[[part canvas.asm | circle_setup: | ; Plot the eight mirror images]]

The eight-way plotting is two calls to plot4, once with (x, y) and once swapped. A filled circle does not plot points at all: for each step it draws horizontal spans of the right width (span8), reusing draw_hline.

[[part canvas.asm | ; Plot the eight mirror images | ; --- Copy the canvas into video]]

A circle may hang over the edge of the canvas, because plot ignores anything outside it. A radius of 0 is handled separately and draws a single pixel; without that check the loop would never end. Rectangles with no width or no height likewise draw nothing.

Flood fill on the tile map

Filling a region is another place where tiles win. Filling pixels one at a time on a 128×128 canvas is a lot of work; filling tiles on a 20×18 map is trivial, and for backgrounds it is usually what you want: a room, a field, a pool.

The fill works on the shadow map. It looks at the tile where it starts, remembers that tile as the one to replace, and then repeatedly visits squares: if a square still holds the old tile, it is changed to the new one and its four neighbours are queued. Walls (any other tile) stop it. The queue is the CPU stack: PUSH a position, POP the next to visit, and stop when the stack pointer is back where it started.

[[part tilemap.asm | flood_fill: | ; --- end of tilemap.asm]]

Two details deserve a second look. A column of $FF (that is, −1) appears when the fill steps off the left of the map, and the unsigned test CP 32 rejects it along with anything past the right edge, so there is no separate negative check. And the very first test, “is the new tile the same as the old?”, prevents an endless loop when asked to fill a region with its own tile.

The stack grows by up to four entries (8 bytes) for each square filled, because neighbours are queued before they are known to be fillable. For the small regions of a 20×18 screen that is fine; do not use it to fill an entire 32×32 map.

[[file flood_demo.asm]]

What you see: a room with a wall down the middle. The left half is covered in dotted tiles; the right half is untouched. The fill stopped at the walls and never leaked outside.

[[shot flood_demo | flood_demo.asm: the left room filled with dotted tiles; the wall stops the fill.]]

Key fact: shapes on a tile map are tile writes — fast and exact. Keep the pixel canvas for curves and detail, and a shadow map in RAM for anything you edit in bulk.
