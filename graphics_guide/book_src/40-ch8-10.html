8. Text & Fonts

[Back to Contents]

In High-Level Languages

Printing text is print("Hello"). Behind it, a font file is loaded and each glyph is rendered (from a bitmap or from outlines) into the framebuffer at the right position, with spacing and line breaks worked out by the library. The cost is hidden, but real: every letter is a small blit.

[[text]] for each character in "Hello": glyph = font[character] blit(glyph, x, y); x += glyph.width [[/text]]

On the Game Boy there is no font file, no glyph renderer and no blit, but the idea of “a picture per character” maps onto the hardware very neatly.

In Game Boy Assembly

The Game Boy contains no font. But it does not need a text-drawing routine either, because a letter is just a tile. If tile number 65 is a picture of an “A”, then putting 65 in the tile map makes an A appear. Printing a string is writing one byte per character into the map — the cheapest drawing operation the machine has.

Loading a font

The font in font.inc stores each glyph as 8 bytes of one-bit-per-pixel rows, 96 glyphs for ASCII 32 to 127. A tile needs two bytes per row. If the same byte is written to both bit-planes, every set pixel becomes colour 3 and every clear pixel colour 0, so the expansion is the cheapest conversion there is: write each byte twice.

The font is loaded starting at tile $20, so that the tile number of any character is its ASCII code. There is no lookup table and no subtraction: "A" is 65 in the string, 65 in the map, 65 as the tile.

[[part text.asm | text_init: | print_at:]]

That leaves tiles 0–31 (and $80–$FF) free for your own use: custom characters, borders, icons. It is worth noticing what the font costs, though: 96 of the 256 tiles in the $8000 range, more than a third. A real game with a lot of artwork puts the font in tiles 128–255 (the $8800 block, which sprites share) and writes its strings with that offset, or loads only the characters it uses. The window cannot pick a different tile block from the background: both follow bit 4 of rLCDC. Font tiles and picture tiles share one numbering, so keep a list of which tile number is which.

Printing

The cursor is a map address in work RAM. print_at computes it from a column and a row (using the same ×32 trick as Chapter 1, relative to whichever map is selected for text), and print_char stores a tile and advances.

[[part text.asm | print_at: | print_char:]]

Unlike the routines in earlier chapters, print_char is safe to call with the LCD on. Before writing it waits for the LCD to leave modes 2 and 3, using the status register rSTAT. Strictly, only mode 3 locks VRAM; modes 2 and 3 both lock OAM. Waiting out both is the simple, safe test, at the price of skipping a little usable time:

[[part text.asm | print_char: | print_string:]]

Strings and numbers are loops over that:

[[part text.asm | print_string: | SECTION "Font"]]

A string is a list of bytes ended by a zero. print_number prints three digits by repeated subtraction: count how many times 100 fits, then 10, then 1. This is much cheaper than a division routine on a CPU with no divide instruction.

Custom graphics in the text

Because text is tiles, an icon is just another tile in the same range. Tiles 1–3 here are a heart, an arrow and a smiley face, printed exactly like letters. Anything in a string can be mixed with them, and the same palette register that recolours the screen recolours the text.

Text boxes in the window layer

Dialog boxes and menus are a good use of the window layer from Chapter 7: it floats above the scrolling background, has its own map, and can be switched on and moved by changing rWY without disturbing what is underneath. text_window points the printing routines at the window's map instead of the background's.

A complete example

This program prints a title and a score, a row of custom glyphs, and a framed message box in the window that is “typed” out one letter every two frames.

[[file text_demo.asm]]

What you see: “HELLO, GAME BOY!” and “SCORE 042” near the top left, three hearts, an arrow and a smiley, and across the bottom a box whose message appears gradually. Note that the typing loop runs with the LCD on: that is what the status check inside print_char is for.

[[shot text_demo | text_demo.asm: text, custom glyphs, and the window message box.]]

One detail in the demo is easy to trip over: print_char uses register A, so the program reloads A before every call, even for the same character.

Key fact: text is not a special feature. Load the glyphs as tiles in ASCII order and printing is one byte per letter into the map.

Try it yourself

  1. Print a 16-bit number as five digits. What is the biggest value print_number can handle now?
  2. Write print_centred, which prints a string in the middle of a row. You will need the length of the string first.
  3. Make the typing effect speed up when a button is held (after Chapter 11) and add a blinking arrow when the message is finished.

9. VBlank, Timing & Smooth Animation

[Back to Contents]

In High-Level Languages

Smooth animation takes a back buffer: draw the whole next frame off-screen, then swap it with the one on show, so the viewer never sees a half-drawn picture. A “vsync” call or a frame timer keeps the loop in step with the display, and games usually measure how long the last frame took so movement stays the same speed on a faster or slower machine.

[[text]] loop: update(game state) draw(everything) into back_buffer wait_for_vsync() swap(front_buffer, back_buffer) [[/text]]

A back buffer costs a second full-screen block of memory, and the full redraw costs time. The Game Boy has no memory to spare for one, which pushes it to a different answer.

In Game Boy Assembly

The Game Boy has no back buffer, and doesn't need one. There is no framebuffer to hold a half-drawn picture: the screen is drawn straight from tiles, the map, the scroll registers and OAM as they stand at the time each line is drawn. A picture is only wrong if the program changes one of those while the LCD is reading it.

The discipline that replaces double buffering is therefore when you change things:

  1. All the thinking — input, movement, collisions, deciding what should change — goes on in the main program, at any time, and writes only to work RAM.
  2. All the touching of video memory happens in VBlank, in one short burst.

The work-RAM copy of OAM (the shadow OAM of Chapter 6) is a back buffer for sprites. A queue of tile changes serves the same purpose for the map.

The shape of a frame

The LCD runs at about 59.7 frames per second. Each frame has 154 lines of 456 clock cycles each: lines 0–143 are drawn, lines 144–153 are VBlank. That gives about 1,140 machine cycles of VBlank and about 16,400 more for everything else, a frame in all of 17,556 machine cycles. A game's frame is a budget of cycles, and VBlank's share is the small, precious part.

So the standard loop is:

[[text]] wait for VBlank copy sprites (OAM DMA, 160 cycles) write the queued map changes update the scroll registers do the game logic for the next frame (go round again) [[/text]]

The VBlank interrupt

Polling rLY (as wait_vblank did) works but keeps the CPU spinning. The better way is the VBlank interrupt: enable it in rIE and the CPU jumps to address $40 at the start of every VBlank. The main loop can then HALT — stop until the next interrupt — which saves battery (it needs interrupts enabled: vblank_init only sets rIE, so the program must also execute EI), and wakes it at exactly the right moment.

[[part vblank.asm | VBlankHandler: | ; Sleep until]]

The handler saves the registers it touches (and restores them before RETI), starts the sprite DMA, flushes the update queue, and tells the main program a frame has begun by setting wVBlank. The main loop's wait_frame sleeps until it sees that flag:

[[part vblank.asm | ; Sleep until | queue_tile:]]

The update queue

Map changes cannot happen at an arbitrary moment, so the main program does not write them: it puts them in a queue. Each entry is a map address and a tile number, three bytes. queue_tile turns a column and a row into an address and appends an entry; the VBlank handler writes them all out.

[[part vblank.asm | queue_tile: | ; Called by the VBlank handler]]

It masks the VBlank interrupt (in rIE) while it adds an entry, and puts rIE back exactly as it found it, so it is safe to call whether interrupts are on or off. Otherwise the handler could run halfway through, empty the queue, and then the main program would finish adding to a queue that no longer matches its own idea of the length. A VBlank that arrives in the meantime is not lost: it stays pending and runs the moment the mask is lifted.

[[part vblank.asm | ; Called by the VBlank handler | ; --- end of vblank.asm]]

The queue holds 16 entries, about 20 cycles each to flush, so even a full queue is over a quarter of the VBlank budget. If the budget matters more than the queue, make it shorter.

A complete example

A ball bounces round the screen and a three-digit frame counter ticks in the corner. The ball is a sprite (moved in the shadow OAM, sent by DMA); the counter is queued tile writes.

[[file anim_demo.asm]]

What you see: a small ball that bounces diagonally off the edges of the screen, and a counter at the top left that increments by one every frame (it wraps at 255). Every change to video memory happens inside the handler: the main loop never touches VRAM.

[[shot anim_demo | anim_demo.asm: the bouncing ball and the frame counter.]]

Measuring how long your frame takes

How close is a program to missing a frame? The simplest meter costs two instructions: set the palette to all black when the work starts, and back to normal when it ends.

[[asm]] LD A, %11111111 LDH [rBGP], A ; the screen goes black ... ; ... the game's work for this frame ... LD A, %11100100 LDH [rBGP], A ; ... and back to normal [[/asm]]

The work starts just after VBlank begins, so the black is hidden while the LCD is not drawing. Anything still running when the first line of the next picture starts shows up as a black band at the top of the screen, and every line of band is another 114 machine cycles of overrun. No band means the work fits inside VBlank; a band reaching halfway down means the frame is in trouble.

Try it: assemble anim_demo.asm with rgbasm -D PROFILE=1. A black band about 14 lines tall appears at the top of the screen, which the test suite measures. A bouncing ball and a counter cost the VBlank period plus another 14 lines — roughly 2,700 cycles, about 15% of the frame. Most of that is not the ball at all: oam_end clears the 39 unused sprites one at a time. That is the profiler doing its job, since it points straight at the first thing worth optimising. Put your game's real workload between the two palette writes to find out how much room is left.

[[shot anim_profile | anim_demo.asm built with PROFILE=1: the black band at the top is the frame overrunning VBlank.]]

Key fact: don't buffer the picture, buffer the changes. Think any time, write video memory only inside VBlank, and let the interrupt and DMA do the writing.

Try it yourself

  1. Add a second ball with its own position and velocity. How many sprites do you use, and what is the first thing that breaks if you add forty?
  2. Show the frame counter in hexadecimal. Which table or calculation turns a nibble into a font tile?
  3. Put a long delay loop into the main loop and assemble with -D PROFILE=1. How tall does the black band get? At what delay does the ball start to stutter?

10. Graphics Optimisation

[Back to Contents]

In High-Level Languages

Optimising graphics code is usually a matter of profiling first, then choosing better algorithms, drawing less (clipping, caching, dirty rectangles), and moving work to the GPU or to vector instructions. The rule is to measure before changing anything, because the slow part is rarely where you expect.

[[text]] start = clock(); draw_scene(); elapsed = clock() - start [[/text]]

On the Game Boy there is no GPU to move work to, no floating point and no multiply, and every instruction has a fixed cost you can look up. That makes the profiling very different: you count cycles, and you aim at one specific budget.

In Game Boy Assembly

On the Game Boy you count cycles by hand — and the cycle count that matters most is the 1,140 of a VBlank. Almost all the real optimisation work is on one question: how many bytes can reach VRAM in that time?

Here are the costs, in machine cycles, of the building blocks:

InstructionCyclesInstructionCycles
LD A, [HL+]2PUSH rr4
LD [DE], A2POP rr3
INC DE2LD [HL+], A2
DEC BC2JR NZ (taken)3

The plain copy

The loop from Chapter 1 does each byte in 13 cycles:

[[text]] LD A,[HL+] 2 LD [DE],A 2 INC DE 2 DEC BC 2 LD A,B 1 OR C 1 JR NZ 3 = 13 cycles per byte [[/text]]

That moves about 87 bytes in one VBlank — four map rows. Most of those cycles are bookkeeping, not copying.

Unrolling

The cure is unrolling: write the copy sequence out many times so the loop test and the 16-bit counter run once per block, not once per byte. Each byte now costs 6 cycles (LD A,[HL+], LD [DE],A, INC DE), more than twice as fast. The assembler does the writing with REPT:

[[part fast.asm | copy_unrolled: | ; Reading with POP]]

The price is size — 16 times 3 instructions — and a restriction: it moves multiples of 16 bytes.

Using the stack as a data pump

The stack instructions move two bytes at once. POP DE reads two bytes from where the stack pointer points and advances it, in 3 cycles, which is cheaper than two single-byte loads. So if the stack pointer is set to the source, a copy is a series of pops, each followed by two stores:

[[part fast.asm | ; Reading with POP | ; Writing with PUSH]]

That is 9 cycles for two bytes: 4.5 per byte. Filling is better still. PUSH BC writes two bytes in 4 cycles and moves downwards, so setting the stack pointer to the end of the area and pushing fills at 2 cycles per byte — about five times faster than the plain fill loop (10 cycles per byte) and over six times faster than the plain copy.

[[part fast.asm | ; Writing with PUSH | ; row * 32]]

These routines have two rules. They disable interrupts (DI) because an interrupt arriving while the stack pointer is aimed at the data would push a return address into the middle of it; and they restore the stack pointer before returning. The caller turns interrupts back on. That also means they cannot be used where an interrupt must arrive on time, or from inside an interrupt handler. A raster-effect handler like the one in Chapter 7 should use the plain routines.

Cheaper address calculation

The map-address routine from Chapter 1 spends five ADD HL, HLs on ×32. There is a faster way using rotation. A row number is 5 bits. Rotated right three times, the low three bits of the row (which, times 32, are the part that lands in the low byte of the address) end up as the top three bits of the byte, and the high two bits of the row (which become the high byte, as row / 8) as the bottom two:

[[part fast.asm | ; row * 32 without | ; --- end of fast.asm]]

The result is the same address in about half the cycles. When a program computes thousands of addresses (a tile-based collision test, a map editor), this is worth having.

Measuring it for real

The timing numbers are not merely calculated: the next program measures them. The register rDIV counts up continuously (once every 64 machine cycles) and any write to it resets it to zero, which makes a handy stopwatch. Each routine is wrapped in a reset and a read:

[[file speed_demo.asm]]

The results, in rDIV ticks of 64 cycles, for 1,024 bytes:

The address comparison: 100 calls of the plain routine took 75 ticks, 100 calls of the rotation version 51 — including the loop around them. The test suite checks the ordering of every result, and that each fast routine produces exactly the same data as the plain one.

The “bytes per VBlank” column is optimistic: the handler also needs the OAM DMA and some margin. A realistic target is 60–70% of the figure. This is why larger transfers (a whole new screen of tiles) happen with the LCD off, or are spread across several frames.

Hardware copying on the Game Boy Color

The Game Boy Color has the thing the original lacks: a general-purpose DMA unit for video memory. Five registers, rHDMA1 to rHDMA5 ($FF51-$FF55), take a source address, a destination address in VRAM and a length in blocks of 16 bytes. Writing the length starts the copy at once, and the CPU simply waits until it is finished — far faster than any loop it could run, so it is how a game loads a screenful of tiles during VBlank. (The exact speed depends on the console mode; see the Pan Docs if you need numbers.)

[[file cgb.asm]]

One trap: the hardware ignores the low four bits of both addresses. If the source is not on a multiple of 16, the copy comes out shifted by the difference, with no error. The data in the example is placed with ALIGN[4] for that reason. The example copies 64 tiles twice, once with the loop from Chapter 1 and once with hardware, and the tests check that the two results are identical byte for byte:

[[file hdma_demo.asm]]

Like cgb_demo it needs rgbfix -c. The emulator performs the copy instantly, so, unlike the other timings in this chapter, no cycle count is quoted for it.

Other savings

  • Do less. The best copy is the one you skip. Update only the tiles that changed (the update queue), not the whole map.
  • Use LDH. LDH A, [rLY] is 2 bytes and 3 cycles; the same read as LD A, [$FF44] is 3 bytes and 4. The same goes for high RAM variables, which you can place with SECTION ..., HRAM.
  • Let the hardware move data. OAM DMA moves 160 bytes in 160 cycles — no loop beats that. The Game Boy Color's block copy (HDMA, above) is another case.
  • Let the LCD be off. Anything big — a title screen, a new level — is loaded with the LCD off and no time limit at all. A fade to white first hides the blank.
  • Look before you wait. The rSTAT check in print_char costs a few cycles per write. Do it per run of writes, not per byte, when you know the run will fit in one safe period.

Key fact: the budget is the VBlank. Spend cycles on moving bytes, not on counting them: unroll, use PUSH and POP to move two bytes at a time, and use the hardware's own DMA wherever it is offered.
