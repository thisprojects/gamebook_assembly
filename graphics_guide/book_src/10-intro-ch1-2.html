Introduction

The original Game Boy was built to do one thing well: put moving pictures on a small, slow LCD, sixty times a second, using a processor that is barely faster than a pocket calculator. It manages this because most of the hard work of drawing is not done by your program at all. The screen is assembled by dedicated hardware from three ingredients you provide: tiles (8×8 pictures), maps (grids saying which tile goes where) and sprites (tiles that float freely above everything else).

That changes how you think about graphics. On many machines you would work out where in memory a pixel lives and change it yourself. On the Game Boy you will rarely touch a pixel directly. You describe the picture — “this tile here, that sprite there, scroll by three” — and the hardware draws it, applying transparency, flipping, clipping and scrolling for free. This book teaches graphics the way the machine wants them taught: ten topics, each starting with the job you want done and showing the Game Boy's own way of doing it, and a last chapter that adds the joypad and ties them into something you can steer. Sound is left for another book, and the link cable and cartridge hardware are not covered.

What you should know first

This book assumes you can read basic Game Boy (SM83) assembly: registers A, B, C, D, E, H, L, the 16-bit pairs such as HL, LD, ADD, CP, the flags, JR and CALL. If you can follow a loop that counts from 1 to 10, you are ready. Everything graphical is explained from scratch.

The three layers

Every frame the LCD draws 144 lines of 160 pixels, each pixel one of four shades. The picture is built from layers, back to front:

  • The background — a 32×32 grid of tiles (256×256 pixels) of which a 160×144 window onto it is visible. Two registers set where that window sits, so scrolling is a matter of changing two numbers.
  • The window — a second, non-scrolling grid that can be laid over the bottom or right of the screen. It is made for score panels and text boxes.
  • Sprites — up to 40 movable tiles (or tile pairs) that sit in front of, or behind, the background. Each has its own position, flip flags and palette.

The graphics memory map

All of it lives in a handful of regions:

AddressWhat it holds
$8000-$8FFFTile pictures, 16 bytes each: tiles 0–255 (used by sprites and, normally, the background)
$8800-$97FFFurther tile pictures, 128 per block
$9800-$9BFFTile map 0: 32×32 tile numbers
$9C00-$9FFFTile map 1: a second 32×32 map (background or window)
$FE00-$FE9FOAM: the 40 sprites, four bytes each
$FF40-$FF4BHardware registers: LCD control, scroll, palettes, window and so on

The first four rows together are the 8 KB of video RAM, or VRAM. The hardware reads it all the time to draw the screen, which is why there are rules about when your program may write to it (Chapter 1).

Building and running the examples

The programs are assembled with RGBDS, the standard Game Boy toolchain. Every program in this book is a complete file in the examples/ folder, and every routine is in lib/. To build one:

[[text]] rgbasm -I lib/ -o tiles_demo.o examples/tiles_demo.asm rgblink -o tiles_demo.gb tiles_demo.o rgbfix -v -p 0xFF tiles_demo.gb [[/text]]

or simply run make tiles_demo.gb in the examples folder, and make run-tiles_demo to open it in an emulator. The listings you read here are not retyped: the book is built from the same files that an automated test suite assembles and runs on an emulated Game Boy, checking what ends up in video memory and on screen.

The shape of every program

Every example begins with the same few lines, kept in boot.inc:

[[file boot.inc]]

The Game Boy starts executing at $100, where there are only four bytes of room before the cartridge header, so the program jumps over it. rgbfix fills the header in afterwards. Code then starts at $150, with the stack placed at the top of the first block of work RAM. hardware.inc gives names to the hardware registers (rLCDC, rSCX and so on) and is used with LDH, the short instruction for the $FF00 page.

The routines are plain files you INCLUDE at the end of a program: gfx.asm for the basics, canvas.asm for drawing, oam.asm for sprites, and so on. Appendix A lists them all. Each chapter ends with a few exercises that use only what has been covered so far.

1. Tiles, Tile Maps & VRAM

[Back to Contents]

In High-Level Languages

A graphics library hands you a canvas: a rectangle of pixels with a function like setPixel(x, y, colour). Somewhere underneath sits a framebuffer, a block of memory with a value for every pixel, and the library turns coordinates into a memory address:

[[text]] address = framebuffer + y * width + x framebuffer[address] = colour [[/text]]

The program owns every pixel. To show something, it writes the pixels itself; to move it, it rewrites them; and to put a character on screen it copies in all of its pixels. That is simple to reason about, but it is expensive: a 160×144 picture at two bits per pixel is 5,760 bytes that must be rewritten whenever anything changes. The Game Boy was designed to avoid exactly that cost.

In Game Boy Assembly

The Game Boy has no framebuffer. 160×144 pixels at two bits each would be 5,760 bytes of dedicated memory plus the time to update it — far more than the machine can afford. Instead, the screen is drawn from tiles, and the only thing the program stores per screen position is a one-byte tile number.

The anatomy of a tile

A tile is an 8×8 picture where every pixel is one of four colours, numbered 0 to 3. That needs two bits per pixel, so a tile is 8 rows × 2 bytes = 16 bytes. The two bits of each pixel are kept in two different bytes of its row: the first byte holds bit 0 of the eight pixels, the second byte holds bit 1, with the leftmost pixel in bit 7.

Here is one row, worked out. Suppose a row should read, left to right, 0 1 2 3 3 2 1 0:

[[text]] pixel colour: 0 1 2 3 3 2 1 0 bit 0 (byte 1): 0 1 0 1 1 0 1 0 = %01011010 = $5A bit 1 (byte 2): 0 0 1 1 1 1 0 0 = %00111100 = $3C [[/text]]

so the row is stored as DB $5A, $3C. Two special cases are worth knowing: a row with both bytes $00 is eight colour-0 pixels, and both bytes $FF is eight colour-3 pixels. A whole tile of $FF is a solid block.

The tile map

The screen shows tiles chosen from a grid, the tile map: 32 columns by 32 rows of one-byte tile numbers, starting at $9800. Entry (column, row) is at:

[[text]] address = $9800 + row * 32 + column [[/text]]

A visible screen is 20 tiles wide and 18 tall, so you see the top-left corner of the map unless you scroll (Chapter 7). The part of the 32×32 grid you cannot see is not wasted: it is where new scenery waits to scroll in.

Notice what the arrangement buys you. The map is simply a linear array: no thirds, no interleaving, no odd address formulae. Moving down a row is adding 32. Because a tile can be used any number of times, a screen full of 360 tiles needs only as many pictures as there are different tiles in it — 20 or 30 for a typical screen.

Which picture does tile number 5 mean?

The tile numbers in the map are looked up in VRAM. Bit 4 of the LCD control register rLCDC chooses between two arrangements. With the bit set (the one used in this book, LCDCF_BG8000), tile n lives at $8000 + n × 16, so numbers 0–255 cover $8000-$8FFF. With the bit clear, numbers are signed and tile 0 is at $9000, giving a second range. Sprites always use the first arrangement.

When you may touch VRAM

The LCD controller reads VRAM while it draws each line. If the CPU writes at the same moment, the write is ignored. So the Game Boy gives you two safe windows:

  • VBlank: after the last visible line (line 143) the LCD spends 10 more line times (lines 144–153) doing nothing. That is about 1,100 machine cycles in which VRAM is yours, once per frame.
  • LCD off: clear bit 7 of rLCDC and the screen goes blank; VRAM is free all the time. This is how a program loads its tiles at start-up, or between levels.

Switching the LCD off is only allowed during VBlank (doing it mid-frame can damage a real console’s screen), so the routines wait first:

[[part gfx.asm | ; --- Wait until the LCD | ; --- Copy BC bytes]]

rLY is the line currently being drawn. wait_vblank first waits for any VBlank already in progress to end, then for the next to begin, so it always returns at the very start of a fresh VBlank — the longest window you can get. It is also how every game paces itself to the screen: once the loop calls wait_vblank, it runs exactly once per frame.

Copying tiles and filling the map

Getting tiles into VRAM is a memory copy. The data sits in ROM, and copy_bytes moves it:

[[part gfx.asm | ; --- Copy BC bytes | ; --- Fill the whole background]]

Changing one map entry means turning (column, row) into an address, which is the formula above: row × 32 is five doublings of HL.

[[part gfx.asm | ; --- HL = VRAM_MAP0 | ; --- Use the same shades]]

A complete example

This program loads five tiles, blanks the map, draws a frame around the edge of the visible screen with tile 3, and places a few other tiles. Read it top to bottom: it is the pattern every later program follows — LCD off, load tiles, build the map, LCD on.

[[file tiles_demo.asm]]

What you see: a box outline around the whole screen, a solid block at column 5, row 5, and in the middle three copies of the same tile in a row, showing four horizontal stripes in four shades. The stripe tile is the one worth studying: its bytes pair up as ($00,$00), ($FF,$00), ($00,$FF), ($FF,$FF), giving colours 0, 1, 2, 3 from the two bit-planes.

[[shot tiles_demo | tiles_demo.asm: a frame of tile 3, a solid block, and three copies of the striped tile.]]

Key fact: the screen is a 20×18 grid of one-byte tile numbers pointing at 16-byte pictures. To change what is on screen, change a number in the map — and do it with the LCD off or in VBlank.

Try it yourself

  1. Change the frame so it is two tiles thick. Which tile numbers do you need to write, and in which rows and columns?
  2. Add a fifth tile of your own design (a smiley face, say) and place it in a pattern across a row. How many bytes did you have to write to the map, and how many to tile memory?
  3. Switch the background to the second map at $9C00 by setting bit 3 of rLCDC (LCDCF_BG9C00), draw something different in that map, and flip between the two with a button press once you have read Chapter 11.

2. Palettes & Shades

[Back to Contents]

In High-Level Languages

A pixel in most graphics libraries carries its colour with it: three numbers for red, green and blue, or an index into a palette array. Changing the colour of something on screen means finding every pixel that has that colour and rewriting it, or, if the library uses indexed colours, replacing an entry in the palette array and redrawing.

[[text]] for each pixel on screen: if pixel == old_colour: pixel = new_colour [[/text]]

The cost is proportional to the number of pixels. A fade across a whole screen therefore means touching every pixel several times, which is why many libraries lean on the graphics card to do it.

In Game Boy Assembly

A Game Boy pixel is not a shade but a colour number from 0 to 3. The shade you actually see comes from passing that number through a palette register. There are three on the original Game Boy:

RegisterAddressUsed by
rBGP$FF47Background and window
rOBP0$FF48Sprites with the palette bit clear
rOBP1$FF49Sprites with the palette bit set

The palette byte

A palette byte holds four 2-bit shades, one for each colour number, with colour 0 in the lowest two bits:

[[text]] bits 7-6 bits 5-4 bits 3-2 bits 1-0 colour 3 colour 2 colour 1 colour 0 [[/text]]

Each shade is 0 (lightest) to 3 (darkest). The usual value is %11100100 — colour 3 maps to shade 3, colour 2 to 2, colour 1 to 1 and colour 0 to 0, so everything looks as drawn. Other values remap the whole screen in one instruction:

  • %00011011 reverses the order: a negative image.
  • %00000000 turns every colour into the lightest shade: a white-out.
  • %11111111 makes everything black.

Because the map stores tile numbers and tiles store colour numbers, a single write to rBGP changes every pixel on the screen. There is nothing to redraw.

Fades and flashes

Fading out is a short sequence of palette bytes where each is a step lighter than the last. Colour 3 drops to shade 2, colour 2 to shade 1, and so on, finishing at all-white:

[[text]] %11100100 normal %10010000 one step lighter %01000000 two steps lighter %00000000 white [[/text]]

The fade table is just a list of bytes to write, one per few frames. This program shows four vertical bands, one for each colour, and walks the table down and back every second:

[[file palette_demo.asm]]

What you see: four bands that fade together to white and return. Look at what the program does not do: after the first frame it never touches a tile or the map. The main loop does a single LDH [rBGP], A per step.

[[shot palette_demo | palette_demo.asm at the start of its fade: the four colours as four bands.]]

Sprites have their own palettes, and there is one important difference: for a sprite, colour 0 is transparent, whatever palette it is given. That is the whole transparency system (Chapter 6). Two sprite palettes let you give two kinds of sprite different looks without creating a second set of tiles.

One palette, no clashes

Because the palette applies to the whole screen, and every pixel is free to be any of the four colours, there is no restriction on where each colour can appear. Any 8×8 tile can use all four. You never have to arrange artwork around a colour grid — draw whatever you like and the tiles hold it.

Game Boy Color

The Game Boy Color extends this idea instead of replacing it. There are eight background palettes and eight sprite palettes, each of four colours chosen from 32,768 (15 bits: five each of red, green and blue). A second layer sits beside the tile map: an attribute map, one byte per tile, kept in a second bank of VRAM. The byte names which of the eight palettes that tile uses and can also flip it or choose a second tile bank.

  • Colours are written through a pair of registers: rBCPS picks the byte of palette memory to write (set bit 7 to count up automatically after every write) and rBCPD receives the data. Each colour is two bytes: 0bbbbbgggggrrrrr, low byte first. Like VRAM, palette memory cannot be written while the LCD is drawing (mode 3), so the demo sets it up with the LCD off.
  • Bit 0 of rVBK chooses which bank of VRAM you are talking to. Bank 0 holds tiles and the tile map as before. Bank 1 holds the attribute map at the same addresses as the map.

This demo paints the same four tiles twice: the top half of the screen uses palette 0 (white, red, green, blue), the bottom half palette 1 (black, yellow, cyan, magenta).

[[file cgb_demo.asm]] [[shot cgb_demo | cgb_demo.asm on a Game Boy Color: the same four tiles with palette 0 (top) and palette 1 (bottom).]]

Build it with rgbfix -c (the supplied Makefile does) so the cartridge header says it supports colour; on a colour console the boot ROM then leaves the colour hardware switched on. The rest of this book uses the original four-shade Game Boy; everything in it also runs on a Game Boy Color.

Key fact: pixels hold colour numbers; a palette register turns numbers into shades. Change the palette byte and you change the whole screen at once, with no pixel touched.
