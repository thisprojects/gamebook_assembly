6. Sprites

[Back to Contents]

In High-Level Languages

A sprite is an object with an image and a position, and the engine draws it every frame. Behind the scenes the engine blits (copies) the image onto the screen, skips transparent pixels, trims anything that hangs over the edge, and either redraws the whole scene or remembers the background under the sprite so it can restore it afterwards. Overlapping sprites need a drawing order.

[[text]] for each sprite, back to front: for each pixel of its image: if pixel is not transparent and (x, y) is on screen: screen[y][x] = pixel [[/text]]

The expensive parts are the copying and the bookkeeping, both proportional to the sprite's area, and both done by the program every frame.

In Game Boy Assembly

On the Game Boy the sprites are in the hardware. You do not draw them; you list them. The LCD controller keeps a table of 40 sprites, and for every line of the screen it looks through the table, finds the ones that cross that line, and draws them over the background. Transparency, clipping at the edges, flipping and layering are all done as part of drawing the line. There is no erasing, because nothing was ever written to the background.

The sprite table (OAM)

Each sprite is four bytes in OAM, object attribute memory, at $FE00-$FE9F:

ByteMeaning
0Y position + 16
1X position + 8
2Tile number (always from the $8000 tile range)
3Flags: bit 7 behind-background priority, bit 6 flip vertically, bit 5 flip horizontally, bit 4 palette (rOBP0 or rOBP1)

The offsets of 16 and 8 are what let sprites slide smoothly on and off the screen: Y = 16 puts a sprite's top at the top of the screen; Y = 0 is entirely above the screen, which is how you hide a sprite. X = 8 puts it flush against the left edge; X = 0 is hidden.

The hardware also does the following without any code from you:

  • Transparency. Colour 0 is always transparent. Draw sprites with a colour-0 background and there is nothing to mask: there is no AND-and-OR dance with a second image.
  • Clipping. A sprite partly off any edge shows only the part that is on screen. A sprite can slide in from the left or out through the bottom with no checking.
  • Flipping. Bits 5 and 6 mirror the tile. A symmetric character needs only half its art: draw the left half once and use it twice, the second time flipped.
  • Priority. With bit 7 set, the sprite appears behind background colours 1–3 (but in front of colour 0), so characters can walk behind trees and doorways.

The limits

There are 40 sprites in total, and at most 10 on any one scanline. If an eleventh crosses a line it is not drawn on that line — the sprites that come later in the table lose. That is why a large character is usually built from tiles that sit on different lines of the screen, and why games that need many sprites in a row shuffle the table order each frame so no single one always disappears.

By setting bit 2 of rLCDC (LCDCF_OBJ16) every sprite becomes 8×16: two tiles tall, taken as an even/odd pair. This is useful for tall characters, and costs nothing in the sprite count. Most examples here use 8×8; the one in Chapter 11 uses the tall mode.

The shadow OAM and DMA

OAM, like VRAM, can only be written safely at certain times. During the LCD's scan of the sprite table the CPU is locked out. The solution is to keep a copy of the table in work RAM — the shadow OAM — to update that at leisure, and to have the DMA hardware copy the whole 160 bytes into OAM once per frame, in VBlank.

Writing a value to rDMA ($FF46) starts a copy of 160 bytes from $XX00 (where XX is the value) into OAM. It takes 160 machine cycles, much faster than a loop would, but during those cycles the CPU can only reach high RAM ($FF80-$FFFE), so the routine that starts the transfer has to run from there. The program copies it into place at start-up:

[[part oam.asm | SECTION "OAMDMACode" | SECTION "OAMRoutines"]]

The shadow buffer sits at an address ending in $00 (ALIGN[8]), which is a rule of DMA: the source address is a high byte and nothing else. LOAD ... HRAM tells the assembler that the code is stored in ROM but will run at an HRAM address, so hOAMDMA is the place to CALL it from.

Adding sprites to the list

A frame starts by emptying the list, adds a sprite for everything that should appear, and ends by hiding all unused entries. oam_add converts screen coordinates to the offset form and writes four bytes:

[[part oam.asm | oam_add: | draw_metasprite:]]

Adding 16 and 8 happens in 8-bit arithmetic on purpose. A sprite whose x is, say, 250 (that is, −6 as a signed number) is stored as 258 − 256 = 2, which is the hardware’s way of saying “six pixels hanging off the left edge”. The wrap-around is exactly what we want, and it is why a sprite can enter the screen from the left with no special case.

Metasprites

Most characters are bigger than 8×8, so they are groups of sprites that move together: metasprites. A definition is a count and then, for each part, an offset from the group's origin, a tile and the flags. draw_metasprite adds all the parts at a position:

[[part oam.asm | draw_metasprite: | oam_end:]]

Because flipping is free, a symmetrical figure is described with the same tile twice:

[[asm]] InvaderA: DB 2 ; two parts DB 0, 0, 3, 0 ; y offset, x offset, tile 3, no flags DB 0, 8, 3, OAMF_XFLIP ; 8 pixels to the right: tile 3 mirrored [[/asm]]

Animation is picking a different metasprite (or different tile numbers) each frame. There is no need to redraw or erase anything.

A complete example

Three rows of animated invaders march across a checkerboard, and a UFO enters from the left edge and leaves through the right, using the hardware's clipping for both. The invaders are two tiles wide but only one tile of artwork is stored: the right half is the left half flipped. Every 16 frames the artwork changes between two tile numbers.

[[file invader.asm]]

What you see: ten sprites in total: three invaders of two sprites each, a fourth invader walking along the bunker row, and the UFO. The checkerboard shows through the transparent pixels of each sprite. The UFO's x position is computed as wUfoX - 16 in 8-bit arithmetic, so as wUfoX counts from zero it starts off the left edge (a “negative” x) and slides in, with the hardware clipping the portion that is still outside. At the other end it leaves the same way.

[[shot invader | invader.asm: marching invaders, the UFO, and the invader hiding behind a bunker.]]

Notice the main loop: wait_vblank, then hOAMDMA to send the previous frame's list, then work out the new frame's list. Updating the shadow and copying it a frame later is what makes sprites appear and move without any flicker or tearing.

Behind the scenery, and a second palette

Two more flags in the same byte give a sprite a place in the scene. The priority bit (OAMF_PRI) puts a sprite behind every background pixel that is not colour 0. Sprites still show through the empty parts of the background, but the bunker tiles in front of them hide them. That is how a character walks behind a tree, a doorway or a wall, and it costs nothing: the fourth invader in the example is an ordinary sprite with one extra flag on each of its two halves. The bunkers use background colour 2, which is how they hide the invader; the checkerboard behind uses colour 1, so the invader is also half hidden there, as the screen shows. Draw scenery you want to walk behind in colours 1–3, and leave the empty background as colour 0.

The palette bit (OAMF_PAL1) chooses rOBP1 instead of rOBP0 for that sprite. In the example rOBP1 is set to %00011011, the reverse of the normal palette, so the UFO's solid body comes out in the lightest shade where the invaders' is the darkest. Two kinds of sprite look different without a single extra tile.

More than ten sprites on a line

The limit of ten sprites per line is a hardware fact, and a program that has more has to decide who loses. The hardware always keeps the first ten in table order, so the plain approach, adding sprites in the same order every frame, means the last ones in the list are never seen on that line. The usual cure is to rotate the order: each frame, start the table one sprite further along. No sprite is lost for good. Each is missing on a few frames out of fourteen, which the eye reads as a mild flicker rather than as a sprite that has vanished.

This demo puts fourteen sprites on a single scanline. Press A to turn the rotation off and on: with it off, the same ten are drawn and four never appear; with it on, all fourteen appear and the missing four keep changing.

[[file flicker_demo.asm]]

What you see: a row of blocks that shimmers, with a different handful missing on every frame. The test suite counts the blocks on the line frame by frame: exactly ten each time, and over fourteen frames all fourteen positions have been drawn.

[[shot flicker_demo | flicker_demo.asm: fourteen sprites on one line, only ten drawn on any frame.]]

Key fact: sprites are a table, not a drawing operation. Write four bytes per sprite into a RAM copy, let DMA move it during VBlank, and the hardware does the transparency, clipping, flipping and layering.

7. Scrolling

[Back to Contents]

In High-Level Languages

Scrolling a scene means shifting the whole picture. A simple engine redraws everything with a camera offset subtracted from each position; a smarter one copies the existing pixels sideways and draws only the new strip at the edge. Tile-based engines keep a large map of tiles and a camera, and draw only the tiles that overlap the screen.

[[text]] for each visible tile column c and row r: draw tile map[r][c + camera / tile_width] at (c * 8 - camera mod 8, r * 8) [[/text]]

Either way, the cost is proportional to the area of the screen and is paid again every frame the camera moves.

In Game Boy Assembly

The Game Boy scrolls in the display hardware. Two registers, rSCX and rSCY, say where in the 256×256 background map the top-left corner of the screen sits. Writing a new value moves the entire picture, at no cost to the CPU, by one pixel or by 200. The map wraps in both directions, so scrolling past the right edge shows the left edge again.

[[asm]] LDH A, [rSCX] INC A LDH [rSCX], A ; the whole screen moves one pixel left [[/asm]]

Streaming a world through the map

The map is 32 tiles wide but the screen shows 20, so there are 12 columns outside the view. A world much wider than the map is handled by streaming: as the camera moves, the program writes the next column of the world into the map just before it scrolls into view — and it can overwrite the one that is leaving, which is already off the other side. The map becomes a ring buffer.

When the camera is at pixel camX, the columns visible are camX / 8 up to camX / 8 + 19. So every time camX reaches a multiple of 8, the program has to store world column camX / 8 + 20 into map column (that number mod 32). It is a single column of 18 bytes: about 150 cycles, well inside the VBlank budget.

The world here is stored as a table of heights: sky above, a grass tile at the surface and ground below. The assembler generates the table at build time with a FOR loop:

[[part scroll.asm | ; Tiles: 0 = sky | WorldHeights:]]

and the table itself:

[[part scroll.asm | WorldHeights: | ; --- end of scroll.asm]]

A map column is 32 bytes apart (one per row), so the routine adds 32 to its pointer for each row it writes. Vertical scrolling is the same idea turned through 90 degrees: write the next row of 20 consecutive tiles into the map.

The window

Scrolling moves the whole background, including anything you meant to be fixed on screen: a score, a status bar. The window is a second background layer that does not scroll. It draws over the background starting from a position given by rWY (the line) and rWX (the column plus 7), and reads its tiles from the second map at $9C00. Bits 5 and 6 of rLCDC switch it on and select that map.

This example scrolls the camera one pixel per frame, streams new columns, and has a window HUD: a strip along the bottom that stays still.

[[file scroll_demo.asm]]

What you see: rolling hills and grass moving left, with a row of box tiles fixed along the bottom edge. Look at the main loop: the only per-frame scrolling work is incrementing the camera and storing it in rSCX. The column streaming is the occasional extra (every eighth frame).

[[shot scroll_demo | scroll_demo.asm: streamed hills, with the window HUD fixed along the bottom.]]

Writing the scroll register during VBlank, straight after wait_vblank, means the new value applies from the first line of the next frame, so a frame is never drawn half at the old position and half at the new one. That is the whole story of avoiding tearing on this machine.

Scrolling in two directions

A level that scrolls both ways works the same way, with one more routine. A new row is written along the map instead of down it, wrapping at the end of the row, and a world big enough to need rows and columns can no longer be generated from a one-dimensional table. This world is 64×64 tiles stored in ROM (4 KB, generated by the assembler with two nested FOR loops: diagonal paths, flowers on a grid, and grass).

The two routines never calculate an address for each tile. They work out the first source and destination addresses once, then step: 64 bytes on for the next row of the world, 32 bytes on in the map, with a wrap from the bottom of the map to the top, and a wrap along the map row from column 31 back to 0:

[[part scroll.asm | ; --- Scrolling in both directions | WorldData:]]

Which tiles to stream, and when, follows from where the camera is. With the camera at pixel (camX, camY), the left edge of the screen is tile column camX / 8 and the top edge is tile row camY / 8. Each pixel step is compared with the previous one, and only when it crosses into a new tile is something streamed:

  • moving right: the column just beyond the right edge, camX / 8 + 20;
  • moving left: the column at the left edge, camX / 8;
  • moving down: the row just below the screen, camY / 8 + 18;
  • moving up: the row at the top edge, camY / 8.

A new column is 19 tiles tall (one more than the 18 rows on screen, since the scroll can leave part of a nineteenth showing), and a new row 21 tiles long. The demo walks the camera round a square, so every one of the four cases is exercised:

[[file scroll2d_demo.asm]]

What you see: a field of grass with diagonal paths and flowers, scrolling right, then down, then left, then up, returning to where it started. The test suite compares every visible tile in the map with the world's own formula, at forty moments along the route.

Raster effects: changing the scroll mid-frame

Because scrolling is a register, nothing stops you changing it while the screen is being drawn. The LCD can interrupt the CPU when it reaches a chosen line: write the line number to rLYC, set bit 6 of rSTAT and enable the STAT interrupt. The handler then changes rSCX and the lines below the split use the new value. This is how games get parallax: distant parts of the screen scrolling more slowly than near ones.

Here the top half scrolls at half the speed of the bottom half. The VBlank handler sets the scroll for the top region at the start of the frame; the STAT handler, which fires just before line 72, sets it for the bottom. The main loop sleeps with HALT between interrupts and moves two counters.

[[file parallax_demo.asm]]

What you see: two bands of vertical bars, the upper moving at half the speed of the lower, like distant and near scenery. Note how the main loop ignores the STAT interrupt (it wakes the CPU too) by checking the wVBlank flag: it only does the frame's work when the VBlank handler says a new frame has begun.

[[shot parallax_demo | parallax_demo.asm: the top band scrolls at half the speed of the bottom band.]]

Raster effects need care: the handler must be short, because it runs during the visible part of the frame, and it should keep to a simple register write or two. The same trick, with a table of values, produces wobbling water and heat-haze.

Key fact: scrolling is two registers and a ring-buffered map. Write the new column just ahead of the screen, change rSCX during VBlank, and use the window for anything that must stand still.
