11. Input & a Playable Character

[Back to Contents]

In High-Level Languages

Input arrives as events or as a state you can ask for: if (keyboard.isDown(RIGHT)) player.x += speed. The operating system has already turned the electrical signals into key codes and queued them. The program asks “is this key down?” and sometimes “was it pressed this frame?”.

In Game Boy Assembly

The Game Boy has no operating system and no event queue. There are eight buttons wired as a matrix, and one register, rP1 ($FF00), to read them. You tell the register which group of buttons to connect — the direction pad or the four buttons — and then read four bits back.

Write to rP1SelectsBits 3–0 read back
bit 4 lowDirection padDown, Up, Left, Right
bit 5 lowButtonsStart, Select, B, A

A pressed button reads as 0, so the routine inverts what it reads. It does this twice, once per group, and joins the results into one byte with one bit per button. The “settling” reads, three of them in a row, are real: the lines take a moment to change after you select a group.

Held and pressed

The routine keeps two bytes. wJoy is every button held right now: use it for movement, where holding right should keep you moving. wJoyNew is only the buttons that went down since the previous call. It is worked out by inverting last frame's state and AND-ing it with this frame's: a bit survives only if the button is down now and was not down before. Use it for anything that should happen once per press: jump, fire, a menu choice. Without it, holding the button for twenty frames would do the action twenty times.

Call read_joypad once per frame, straight after the frame begins, and every part of the program then agrees about which buttons were down on that frame.

Tall sprites

A character is usually taller than it is wide. Setting bit 2 of rLCDC (LCDCF_OBJ16) switches every sprite to 8×16: each sprite entry now draws two tiles stacked vertically, the number in the entry and the one after it (the lowest bit of the tile number is ignored, so use an even number). One sprite entry now does what two did, and the hardware's rule of ten sprites per line is easier to live within. The mode applies to all sprites at once; you cannot mix sizes.

Walls: looking at the map

To keep a character out of walls you need to know what is where. The Game Boy gives you the answer for free, because the world is the tile map. A pixel position (x, y) is on the map square (x / 8, y / 8), and the tile number stored there says what it is. So a collision test is: divide by eight, look up a tile, compare it with the wall tile number. No bounding boxes, no pixel comparison.

Video memory cannot be read at any moment, and reading it from the main loop would be unsafe, so the program checks against its shadow map in RAM (Chapter 4), which is also what it drew the room from. The player's box is 8 pixels wide and 16 tall, and because no tile is bigger than the box, the four corners and the middle of the left and right sides are enough: six map lookups tell whether any part of the box is inside a wall.

The order matters: the program works out where a step would end up, asks whether that spot is free, and only then moves. Each direction is tested separately, so pressing diagonally into a wall slides along it instead of sticking:

wall_at ends with a CP and then a POP, which does not touch the flags, so the zero flag it produced survives the return: Z means “wall”. The 8-bit arithmetic does the edge checks for free: the room has a border of wall tiles, so the player can never leave the screen.

A walk cycle

Animation is only changing which tile numbers the sprite uses. Every step the player takes adds one to wAnim. Bit 3 of that counter is zero for eight steps and one for the next eight, so the player swaps between two pairs of tiles every eight steps while moving, and holds the last pose when stopped. Turning bit 3 into a tile number is two rotations (8 becomes 2) and an add of 4.

A complete example

The player is one 8×16 sprite in a walled room with a wall across the middle, steered by the direction pad. Holding B makes it run at two pixels a frame; pressing A turns it round, using the horizontal flip flag. The frame loop is the one from Chapter 9, the room is drawn with the line routines of Chapter 4, and the checks above keep it inside.

[[file walker_demo.asm]]

What you see: a tall figure on a checkerboard floor inside a brick border, with a wall of bricks across the middle. It walks, swaps its legs as it goes, stops at the walls, can walk round the end of the middle wall, and turns round when you press A. The loop is too long for a relative jump, so it ends in JP where the shorter programs use JR.

The test suite steers the figure by pressing buttons in the emulator. It checks its position after each move, that it stops against the middle wall from both sides and against the border, that the walk frames really alternate, and that holding A turns it round exactly once.

Where to go next

This chapter has everything a small game needs: a tile map for the world, sprites for characters, scrolling for large levels, a window for the HUD, text, a frame loop, input, and collision with the map. Put the pieces together: scroll the room, give it a HUD, add enemies that move by the same rules as the player. The Game Boy's sound hardware, with four channels and their own registers, is the subject of a separate book and is not covered here.

Key fact: input is one register read twice, inverted. Keep both “held” and “newly pressed”, and read the pad once per frame.

Try it yourself

  1. Add a gap to the middle wall (clear two tiles of it in the shadow map) and walk through it. How tall is the smallest gap the player fits through, and why?
  2. Add a second tile type, water, that the player can walk on at half speed. Where do you look it up, and where do you change wSpeed?
  3. Add a second sprite that follows the player with a delay. Where do you store the history of positions?
